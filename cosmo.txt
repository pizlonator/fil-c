# Building Fil-C in cosmo mode and producing fat APE binaries

The cosmo flavor is the third libc flavor of Fil-C, next to the musl and glibc
flavors.  It uses [cosmopolitan libc](https://justine.lol/cosmopolitan/) (cosmo)
on both sides of the Fil-C sandwich: cosmo is the yolo (un-pizlonated) libc
below libpizlo, and it is also the user libc above it (rebuilt by the Fil-C
compiler).  Cosmo-mode programs are static, non-PIE executables with no dynamic
linker, and every cosmo-mode link produces a fat "actually portable
executable" (APE): one file that runs on multiple operating systems and on
both x86_64 and ARM64.

Like the other flavors, cosmo mode is selected entirely by what is installed in
`pizfix/`.  The compiler itself is flavor-blind: at startup it probes
`pizfix/lib/libyolocosmo.a`, and if that file exists it links cosmo-style
(static, non-PIE, via cosmo's APE linker script) and post-processes the link
into a fat APE.  No reconfigure or rebuild of LLVM/clang is needed to switch
flavors.

Everything below was verified against the scripts and binaries in this tree,
on a Linux/X86_64 host (the cosmo APE tooling installed into
`pizfix/libexec/` is built as x86_64 Linux binaries, so that is the host this
flavor is exercised on).  For the aarch64 half of the story you also want:

```
sudo apt-get install gcc-aarch64-linux-gnu libc6-dev-arm64-cross \
    linux-libc-dev-arm64-cross libstdc++-13-dev-arm64-cross \
    qemu-user unzip
```

`gcc-aarch64-linux-gnu` provides `aarch64-linux-gnu-ld` (plus the aarch64
cross compiler and its runtime), `libc6-dev-arm64-cross` and
`linux-libc-dev-arm64-cross` provide the aarch64 glibc and kernel headers
that the cross compiler-rt and libpas builds compile against,
`libstdc++-13-dev-arm64-cross` provides the aarch64 C++ standard library
headers used by the C++ parts of the cross compiler-rt build (on a distro
whose cross gcc is GCC 12, like Ubuntu 22.04, install
`libstdc++-12-dev-arm64-cross` instead), `qemu-user` provides `qemu-aarch64`
for running aarch64 binaries on an x86_64 host, and `unzip` is needed by
cosmo's build on first use.

This is exactly what the dev container created by `./enter_container.sh`
installs; the package set was verified on Ubuntu 24.04, where
`./build_all_fast_cosmo.sh` builds and passes the full test suite.

## TL;DR

Build Fil-C in cosmo mode (full build + test suite):

```
./build_all_fast_cosmo.sh
```

Build one fat x86_64 + aarch64 APE (this is just the default link - no
special flag required):

```
build/bin/clang -o hello hello.c
./hello
```

That's it.  `hello` is a single fat APE that runs on x86_64 and aarch64
Linux, macOS, and the BSDs, and on x86_64 Windows.  (`--filc-fat-ape` is
still accepted as an explicit spelling of the default.)  Details below.

## Building Fil-C in cosmo mode

### The scripts

```
./build_all_fast_cosmo.sh     # full cosmo build + filc/run-tests
./build_base_cosmo.sh         # full cosmo build, no tests
```

Both do the same setup and then defer to the shared pipeline:

- `build_all_fast_cosmo.sh` sources `setup_cosmo.sh` and runs
  `./build_all_fast.sh`, which runs `./build_and_test_base.sh` (that is
  `./build_base.sh` followed by `filc/run-tests`).
- `build_base_cosmo.sh` sources `setup_cosmo.sh` and runs `./build_base.sh`.
- `setup_cosmo.sh` just exports `ALTYOLO=./build_yolocosmo.sh` and
  `ALTUSER=./build_usercosmo.sh`, then `build_base.sh` runs the standard
  pipeline with those two hooks in place:
  `rm -rf pizfix`, `build_projeny_yolo.sh`, `build_compiler_rt.sh`,
  `build_yolounwind.sh`, `configure_llvm.sh`, `build_clang.sh`,
  `build_os_include.sh`, `$ALTYOLO`, `build_runtime.sh`, `$ALTUSER`,
  `build_cxx.sh`, `build_minilute.sh`, `build_sarcasm.sh`.

So "building Fil-C in cosmo mode" is the normal Fil-C build with the cosmo yolo
libc (`build_yolocosmo.sh`) and the cosmo user libc (`build_usercosmo.sh`)
plugged into the two alt slots.  The compiler build steps
(`configure_llvm.sh`/`build_clang.sh`) are identical for all flavors.

### What the cosmo-specific scripts build

`build_yolocosmo.sh` (the yolo libc below libpizlo):

- Builds cosmo with cosmo's own bundled GCC per architecture, for every arch in
  `COSMOARCHES` (default: `x86_64 aarch64`), using cosmo mode `<arch>-ape`
  (`make m=x86_64-ape filcyolo`, `make m=aarch64-ape filcyolo` in
  `projects/yolocosmo`; the mode is derived from the arch, there is no separate
  mode variable).  Only a slim subset of cosmo is built - just the objects that
  libpizlo, the crt chain, the user libc, and the C++ runtimes can reference
  (enumerated in `projects/yolocosmo/filc/filc-objects*.mk`, regenerated by
  `projects/yolocosmo/filc/compute-closure.py`).
- Also builds the APE linker tooling (`make filcapetools`): `apelink` and
  `pecheck`, as x86_64 Linux binaries - they only ever run on the build host,
  where the clang driver executes them at link time.
- Installs into pizfix:
  - `pizfix/lib/libyolocosmo.a` (x86_64 yolo cosmo; this file is THE cosmo
    flavor marker), `pizfix/lib/ape.o`, `pizfix/lib/ape.lds`,
    `pizfix/lib/cosmo-crt.o`, `pizfix/lib/ape-x86_64.elf` (the x86_64 APE
    loader that apelink embeds).
  - `pizfix/lib-aarch64/libyolocosmo.a`, `pizfix/lib-aarch64/aarch64.lds`,
    `pizfix/lib-aarch64/cosmo-crt.o`,
    `pizfix/lib-aarch64/ape-aarch64.elf` (aarch64 APE loader; there is no
    `ape.o`/`ape.lds` for aarch64 - apelink generates those headers).
  - `pizfix/libexec/apelink`, `pizfix/libexec/pecheck`,
    `pizfix/libexec/ape-m1.c` (Apple-silicon APE loader source, compiled on
    the fly by Xcode when an APE runs on arm64 macOS).
  - `pizfix/os-include-aarch64/` (symlinks to the aarch64 kernel headers).
  - `pizfix/yolo-include/` (cosmo headers used to compile libpas).
  - For every non-host arch: cross compiler-rt builtins
    (`pizfix/lib-aarch64/libyolort.a`, `crtbegin.o`, `crtend.o`, from
    `compiler-rt/build-aarch64`; only builtins and crt are consumed, so the
    cmake config turns off sanitizers, xray, memprof, ctx-profile, libfuzzer,
    and profile), the cross unwinder
    (`pizfix/lib-aarch64/libyolounwind.a`), and the cross libpas runtime
    (`pizfix/lib-aarch64/libpizlo.a`, `filc_crt.o`, `filc_mincrt.o`, built
    with `make -C libpas FILCARCH=aarch64`).

`build_runtime.sh` rebuilds the **host-architecture** libpas only
(`cd libpas && ./clean.sh && ./build.sh`, i.e. `pizfix/lib/libpizlo.a` +
`filc_crt.o` + `filc_mincrt.o` + the stdfil headers).  The **aarch64** libpas
is built by `build_yolocosmo.sh` (see above), not by `build_runtime.sh`.

`build_usercosmo.sh` (the user libc above libpizlo) rebuilds cosmo with the
Fil-C compiler for every arch in `COSMOARCHES` (default `x86_64 aarch64`) via
`projects/usercosmo/filc.mk`, installing `pizfix/lib/libc.a` (static; `libm.a`
is an empty archive so `-lm` resolves), `pizfix/lib/crt1.o`, and the cosmo
public headers in `pizfix/include/` (arch-neutral, host build only), plus the
same set for aarch64 in `pizfix/lib-aarch64/`.  Incremental builds just work;
force a full rebuild with `FORCE=1 ./build_usercosmo.sh` (useful after editing
a widely-included header, since header dependencies are not tracked).

`build_cxx.sh` probes `pizfix/lib/libyolocosmo.a` to detect the cosmo flavor
and then configures libc++/libc++abi as static archives only (cosmo mode has no
shared libraries).  If `pizfix/lib-aarch64/libyolocosmo.a` also exists, it
additionally cross-builds the aarch64 C++ runtime into `pizfix/lib-aarch64/`.
This is why `setup_cosmo.sh` sets no `ALTLLVMLIBCOPT`: the cosmo detection is
automatic.

### First-build notes

- The first run of `build_yolocosmo.sh` makes cosmo download its own GCC 14.1
  toolchain into `projects/yolocosmo/.cosmocc` (~1.2GB).  This needs network
  access and `unzip`.  After that it is cached and the cosmo yolo build itself
  is quick (seconds per arch when objects are up to date).
- The aarch64 pieces need the cross toolchain and headers installed
  (`gcc-aarch64-linux-gnu`, `libc6-dev-arm64-cross`,
  `linux-libc-dev-arm64-cross`, and the matching
  `libstdc++-13-dev-arm64-cross` — see the package list at the top);
  `build_yolocosmo.sh` symlinks
  `/usr/aarch64-linux-gnu/include/{linux,asm,asm-generic}` into
  `pizfix/os-include-aarch64/`, and the aarch64 cosmo link wants
  `aarch64-linux-gnu-ld` (the driver falls back to `ld.lld` if it is missing).

### Incremental rebuilds

`build_base.sh` starts with `rm -rf pizfix`, so every full run reinstalls
everything from scratch.  If you only changed cosmo-side things, rebuild just
the affected layers, in sandwich order (yolo libc below, then the runtime, then
the user libc, then C++):

```
./build_yolocosmo.sh    # yolo cosmo + APE tooling + cross builtins/unwinder/
                        # cross libpas + yolo-include + os-include-aarch64
./build_runtime.sh      # host-arch libpas (libpizlo.a, filc_crt.o, ...)
./build_usercosmo.sh    # pizlonated user cosmo libc (host + aarch64)
./build_cxx.sh          # static libc++/libc++abi (host + aarch64)
```

Notes on that sequence:

- `build_yolocosmo.sh` must run before `build_usercosmo.sh`: the user libc
  build needs the yolo cosmo artifacts (marker, headers, crt) in place, and
  before `build_runtime.sh` on a fresh tree the stdfil headers it installs are
  needed by the cross libpas build.
- `build_yolocosmo.sh` runs at the very end of its own work.  The bootstrapping
  order inside a full build is: cosmo build + installs, then (for the host)
  `build_runtime.sh`, then `build_usercosmo.sh`; if
  `projects/yolocosmo/filc/compute-closure.py` regenerated the closure lists
  because the runtime or cosmo changed, rerun `build_yolocosmo.sh`'s cosmo
  build so `libyolocosmo.a` contains the new closure.
- `build_runtime.sh` cleans and rebuilds only the host libpas.  If you changed
  something in libpas that also matters for aarch64, rerun
  `./build_yolocosmo.sh` (its tail loop does the `FILCARCH=aarch64` libpas
  build into `pizfix/lib-aarch64`).
- If you only changed the user libc, `./build_usercosmo.sh` alone is enough
  (incremental; objects rebuild only when out of date).  The same is true of
  `build_cxx.sh` for the C++ runtime.
- minilute and sarcasm (`build_minilute.sh`/`build_sarcasm.sh`) are host
  x86_64 tools installed at the end of `build_base.sh`; rebuild them if you
  changed them, but they are not part of the cosmo libc layers.

### Switching flavors

Every run of `build_base.sh` (via any of `build_all_fast*.sh` /
`build_base*.sh`) wipes `pizfix` first, so switching flavors is just:

```
./build_all_fast_cosmo.sh    # cosmo flavor
./build_all_fast_glibc.sh    # glibc flavor
./build_all_fast.sh          # musl flavor
```

The compiler is flavor-blind and needs no rebuild when you switch: it probes
`pizfix/lib/libyolocosmo.a` (cosmo), `pizfix/lib/libc.so.6666` (glibc) etc. at
runtime, per invocation.  `filc/run-tests` does the same probing to decide
which tests to run.

### Time expectations

- `build_yolocosmo.sh` on a warm tree: ~1.5 minutes (the cosmo builds
  themselves are seconds per arch when objects are up to date; the tail of the
  script re-verifies the cross compiler-rt/unwinder/libpas builds).
- The full `build_base_cosmo.sh` on an otherwise-warm tree (LLVM objects
  current) takes minutes.  If clang itself has to rebuild (e.g. you pulled new
  clang commits), the LLVM/clang build dominates (~3,000+ ninja targets, on
  the order of an hour from scratch, ~20 minutes when most objects are warm).
- `filc/run-tests` in cosmo mode: 6445 tests pass on this tree with 124
  skipped (cosmo cannot do shared libraries; see the checklist below), taking
  ~10 minutes on a warm 32-core machine.

## Building programs

Once `pizfix` is in cosmo state (check: `ls pizfix/lib/libyolocosmo.a`), the
stock `build/bin/clang` produces cosmo-mode binaries by default.  The examples
below are run from the repo root with the repo's compiler.

### Default: fat APE plus ELF side files

```
build/bin/clang -o hello hello.c
```

You get three files:

- `hello` - a single fat APE ("actually portable executable", `MZqFpD` magic),
  produced by running `pizfix/libexec/apelink` over the x86_64 and aarch64
  ELF halves as a post-link step.  It runs on x86_64 and aarch64 Linux,
  Windows x86_64, macOS, and the BSDs.
- `hello.com.dbg` - the x86_64 half: a static, non-PIE x86_64 ELF executable
  (`file hello.com.dbg` says `statically linked`, `readelf -h` says `EXEC`,
  and there is no `INTERP` segment: cosmo programs have no dynamic linker).
  This is what the kernel, test tooling, and scripts exec directly.
- `hello.aarch64.elf` - the aarch64 half: a static aarch64 ELF (run it under
  `qemu-aarch64` on an x86_64 host, or exec it directly on arm64).

Compiles get an aarch64 shadow object too:

```
build/bin/clang -c -o hello.o hello.c
```

produces `hello.o` (the x86_64 object you asked for) plus `.aarch64/hello.o`
(the aarch64 "shadow" object, in a `.aarch64/` subdirectory of the output
directory).  The shadow is always produced first and the requested object
last, so build-system dependency tracking on `hello.o` implies that the
shadow is fresh: both files are written by the same invocation, shadow first,
and links consume `hello.o` before `.aarch64/hello.o`.  Separate compilation
just works: `clang -c -o hello.o hello.c && clang -o hello hello.o` gives the
same fat APE as the one-step build.

### Running APEs on Linux

On Linux the kernel refuses to `execve()` an APE (`MZqFpD` is not `ELF`), and
returns `ENOEXEC` ("Exec format error").  Two ways to run one:

- **Just run it from a shell.**  `sh`, `bash`, and friends have an ENOEXEC
  fallback that re-executes the file as a shell script; the APE header
  (`MZqFpD='` ... - the magic is deliberately valid shell syntax) detects this
  and re-launches the embedded payload.  So `./hello` and
  `sh -c './hello args'` work everywhere with no setup.  A raw `execve()`
  (e.g. from Python's `subprocess` without a shell) still fails with
  `ENOEXEC`.  Note that the first shell-run of an APE extracts the APE loader
  into the current directory as a hidden file named `.ape-1.10` (an ELF; it is
  reused on subsequent runs and is safe to delete).
- **Register cosmo's binfmt_misc handler**, so the kernel runs APEs (and
  assimilated ELFs) directly; then any `execve()` works.  See cosmo's
  documentation (`ape/apeloader` / the `binfmt` setup that ships with cosmocc)
  for the one-line registration.
- **Assimilate the APE into a plain ELF** when you need a file the kernel can
  `execve()` directly and do not want to keep the extra artifacts:
  `./hello --assimilate` rewrites the APE in place into a normal
  (single-architecture) x86_64 ELF.

One caveat about running an APE through the loader: the process that the kernel
exec'd is the loader, not your program.  The shell stub does
`exec <loader> <APE-path> <args...>` and the loader loads your program
in-process on a fresh stack, so `/proc/self/exe` is the loader and the kernel's
`/proc/self/cmdline` forever shows `<loader>\0<APE-path>\0<args...>`.  Your
program still sees a normal `argc`/`argv` (with `argv[0]` being the APE path),
but that argv lives outside the region the kernel considers the arg area, so
`zsetproctitle` rewrites it in-process without the kernel ever noticing:
`/proc/self/cmdline` and `ps` keep showing the loader invocation.  That is
inherent to interpreter-style APE execution - binfmt_misc execs the interpreter
the same way - and it is not fixable with `PR_SET_MM`, which is unavailable to
unprivileged programs.  If you need kernel-visible process titles, exec the ELF
sidecar (`<out>.com.dbg`) or build with `--filc-no-ape`.  The `setproctitle*`
tests verify the strict kernel-visibility contract by re-executing the ELF
sidecar next to themselves (`<out>.com.dbg`, or `<out>.dbg` for `--filc-ape`
builds; a candidate is skipped when it is the running image itself, matched by
device and inode, so re-exec'ing the sidecar cannot loop).  The loader-exec'd
APE run still exercises `zsetproctitle` with relaxed checks, and if the
sidecar cannot run (for example an x86_64 sidecar on an aarch64 host) only the
relaxed checks hold: `zsetproctitle` must not panic and the kernel's cmdline
must stay intact.  No loader-name matching is involved.

`hello` (the fat APE) is the default artifact and the one you ship (on Apple
silicon it embeds `ape-m1.c`, which Xcode compiles on the fly).  When you
need a file that the Linux kernel (or a script, or a test harness) can
`execve()` directly, use the `hello.com.dbg` side file.

Validate an APE with the PE checker that the build installed:

```
pizfix/libexec/pecheck hello      # silent, exit 0 on a valid fat APE
```

`pecheck` validates the PE headers (the Windows side of the APE).  It passes
for x86_64 and fat APEs.  Single-architecture aarch64 APEs fail it with
`PE Signature must be 0x00004550` - that is expected, since aarch64 APEs
(linux/macOS/BSD only; Windows is not in the aarch64 support vector) carry no
PE header at all.

### `--filc-ape`: a single-architecture APE

```
build/bin/clang --filc-ape -o hello hello.c
```

Skips the aarch64 half: the APE takes the requested output path and the
x86_64 ELF is kept as `hello.dbg` (this also disables the aarch64 shadow
compiles).  Use this when you want to ship `hello` and keep the ELF only for
debugging, but do not need the aarch64 half.

### aarch64 target

```
build/bin/clang --target=aarch64-linux-gnu -o helloarm hello.c
```

aarch64 builds are single-architecture by design (the two-architecture fat
APE is what the driver builds *for* you when you target x86_64).  The default
aarch64 link produces `helloarm` (an aarch64 APE with the Apple-silicon
loader embedded) plus the aarch64 ELF at `helloarm.dbg`.  Run it on real
arm64 hardware, or on an x86_64 host with qemu (use the `.dbg` ELF for that -
qemu loads ELFs, not APEs):

```
qemu-aarch64 ./helloarm.dbg          # or: qemu-aarch64 ./helloarm.dbg args...
```

(Directly exec'ing an aarch64 binary on an x86_64 host gives `Exec format
error` unless binfmt_misc is registered for aarch64.)

### C++ / libc++

Cosmo mode ships static libc++/libc++abi (no `.so`), and `clang++` works out of
the box:

```
build/bin/clang++ -o prog prog.cpp    # iostream, std::thread, etc.
./prog
```

The C++ tests run in cosmo mode too.  The default fat APE works the same way
with `clang++` (the nested aarch64 compile reads the aarch64 C++ headers that
`build_cxx.sh` installs into `build/include/aarch64-unknown-linux-gnu/`).

### Static-only

Cosmo programs are static, non-PIE executables with no dynamic linker, so:

```
build/bin/clang -shared -o libfoo.so foo.c
# clang: error: 'shared' is not supported in Fil-C cosmopolitan libc mode
# (cosmo programs are static, non-PIE executables with no dynamic linker)
```

The same error covers `-pie` and friends.  `dlopen()` links (cosmo provides a
stub in `libyolocosmo.a`) but always fails at runtime with
`dlopen() isn't supported; consider using cosmo_dlopen() and read its docs`.

## Fat APEs: the default output (and `--filc-fat-ape`)

The headline feature is the default: ONE file that runs on both x86_64 and
aarch64.

```
build/bin/clang -o hello hello.c
```

This produces three files:

- `hello` - a single fat APE (`MZqFpD` magic) containing both the x86_64 and
  the aarch64 images plus the APE loaders.  It runs on x86_64 and aarch64
  Linux/macOS/BSD, and on x86_64 Windows.
- `hello.com.dbg` - the x86_64 ELF (the kernel-executable flavor of the
  x86_64 half).
- `hello.aarch64.elf` - the aarch64 ELF (run it under
  `qemu-aarch64 ./hello.aarch64.elf` on an x86_64 host, or exec it directly on
  arm64).

`--filc-fat-ape` is still accepted and does exactly what the default does
(it cannot be combined with `--filc-ape` or `--filc-no-ape`, and it works for
C++ too: `clang++ --filc-fat-ape -o prog prog.cpp`).

Verified session on this repo:

```
$ build/bin/clang -o hello hello.c
$ ls -la hello hello.com.dbg hello.aarch64.elf
$ ./hello fat-run one two
Hello from cosmo (3 args)
arg 1: fat-run
arg 2: one
arg 3: two
$ echo $?
42
$ qemu-aarch64 ./hello.aarch64.elf fat-run-qemu
Hello from cosmo (1 args)
arg 1: fat-run-qemu
$ head -c 6 hello | od -c          # MZqFpD magic first
0000000   M   Z   q   F   p   D   =   '
$ pizfix/libexec/pecheck hello     # exit 0
$ file hello hello.com.dbg hello.aarch64.elf
hello:            DOS/MBR boot sector  (the APE)
hello.com.dbg:    ELF 64-bit LSB executable, x86-64, statically linked
hello.aarch64.elf: ELF 64-bit LSB executable, ARM aarch64, statically linked
```

Compiles participate too: a default `clang -c -o hello.o hello.c` produces
`hello.o` plus the aarch64 shadow object `.aarch64/hello.o` (see "Default:
fat APE plus ELF side files" above).  That is what makes separate compilation
work: the aarch64 half of a link whose inputs are objects is produced by
re-linking those shadows.

How it works (for context): a clang driver invocation builds one action graph
for one target, so the aarch64 half is produced by a nested full-pipeline
clang invocation (`--target=aarch64-linux-gnu --filc-cosmo --filc-no-ape`
over your original arguments, so all of your other command-line flags are
reused).  For source inputs, that child recompiles every source with Fil-C
codegen and links the aarch64 cosmo libraries from `pizfix/lib-aarch64` to
`<output>.aarch64.elf`.  For object inputs, the aarch64 link instead consumes
the `.aarch64/` shadow objects (the driver rewrites the input paths to their
shadows and adds `<dir>/.aarch64` to the `-L` search paths).  The x86_64 half
links to `<output>.com.dbg`, and finally `pizfix/libexec/apelink -V -1 -l
pizfix/lib/ape-x86_64.elf -l pizfix/lib-aarch64/ape-aarch64.elf -M
pizfix/libexec/ape-m1.c -o <output> <output>.com.dbg <output>.aarch64.elf`
merges both images plus the loaders into the fat APE.  Run any link with `-v`
to see all of the commands.

The aarch64 half is best-effort: anything that keeps it from being built
degrades the link to an X86_64-ONLY APE with a warning (the binary still
runs on x86_64).  That happens when:

- the aarch64 cosmo libraries are missing from the pizfix tree
  (`pizfix/lib-aarch64/libyolocosmo.a` was not built - e.g. a
  `COSMOARCHES="x86_64"` build);
- an input has no shadow: foreign `.o`/`.a` files that this driver did not
  build, x86-only assembly, or bitcode;
- an input's shadow is stale: the driver refreshes the shadow's mtime after
  the primary object is written (a `/bin/touch` command that runs last in
  every compile job), and the link accepts a shadow only if it is at least
  as new as its primary object.  A primary rebuilt without its shadow -
  with `--filc-no-ape`, or restored by a compilation cache that does not
  know about shadow objects, like ccache - therefore degrades to an
  x86_64-only APE with a warning instead of silently mixing old aarch64
  code with new x86_64 code;
- the aarch64 half itself fails.

A failed aarch64 command also cleans up after itself: the partial or stale
output of a best-effort command is deleted before the build continues, so
nothing downstream ever consumes an aarch64 artifact that a failed command
left behind.

Only missing APE tooling (`pizfix/libexec/apelink` or the loaders) falls back
further, to a plain x86_64 ELF at `<output>`, also with a warning.

Archives deserve a note: the driver creates shadow objects, not archives, so
a user archive that the aarch64 link should consume needs its own shadow
archive at `<dir>/.aarch64/<name>.a` (same members, aarch64 target).  A build
system that archives Fil-C objects has to build those shadow archives
itself; without them, the link degrades to the x86_64-only APE per above.

The knobs:

- `--filc-no-ape` - the public off switch for all of this.  Links produce a
  plain single-architecture ELF executable and compiles produce only the
  requested object (no `.aarch64/` shadows, no side files).  This is what
  builds of the cosmo runtime itself use - libpizlo (libpas/Makefile), the
  pizlonated cosmo libc (projects/usercosmo/filc.mk), and the C++ runtimes
  (build_cxx.sh) - since those build each architecture explicitly and must
  not double-compile or leave shadow directories behind.
- `--filc-ape` - a single-architecture APE at `<output>` with the x86_64 ELF
  at `<output>.dbg` (it also disables the shadow compiles).
- `--filc-fat-ape` - accepted for compatibility; this is the default.

## Running on macOS (Apple Silicon)

How a cosmo APE (single-arch aarch64 or fat) actually starts on arm64 macOS:
the file is a shell script first (`MZqFpD='` magic), and on Darwin the stub
takes the `/Applications`-test branch that compiles the Apple-silicon APE
loader **from source, on the user's Mac, on first run**.  apelink embeds the
loader source (`ape-m1.c`) gzip'd into the APE; the stub does:

```
t="${TMPDIR:-${HOME:-.}}/.ape-1.10"
dd if="$o" skip=... count=... bs=1 | gzip -dc >"$t.c.$$";  mv "$t.c.$$" "$t.c"
cc -w -O -o "$t.$$" "$t.c" ||exit                          # on the Mac
mv -f "$t.$$" "$t";  exec "$t" "$o" "$@"
```

Why source, not a prebuilt loader: XNU on arm64 enforces code signing, so a
loader embedded by a Linux build host could never run there (see the comment
in `projects/yolocosmo/tool/build/apelink.c`, "xnu on arm64 has strict code
signing requirements ... we do is embed the ape loader source code and then
hope the user has a c compiler installed").  `ape-m1.c` is a real macOS
program: it includes `<assert.h>` (line 25), `dispatch/dispatch.h`,
`libkern/OSCacheControl.h`, `sys/sysctl.h`, etc. - the whole macOS SDK
surface.  If the systemwide `ape` loader is installed (the stub tries
`type ape` first, and also a previously self-extracted `$TMPDIR/.ape-1.10`),
none of this happens.

**The macOS SDK requirement.**  The stub invokes plain `cc -w -O` with no
`-isysroot`/`SDKROOT` and no probing of `xcrun` (checked in apelink.c both in
our tree and in the 3.9.2 toolchain) - by design, since Apple's `cc` finds its
own SDK.  On a Mac whose `cc` cannot find an SDK (Command Line Tools not
installed, or `xcode-select` pointing at a broken/partial install), that
compile fails with exactly:

```
/var/folders/.../T//.ape-1.10.c:25:10: fatal error: 'assert.h' file not found
#include <assert.h>
```

(The stub only prints its own `please run: xcode-select --install` hint when
`cc` is missing entirely; a `cc` that exists but has no SDK gets the bare
compile error above.  Reproduced on a Linux box with no Apple SDK:
`clang -target arm64-apple-macos -nostdinc -c .ape-1.10.c` yields the same
`.ape-1.10.c:25:10: fatal error: 'assert.h' file not found` - so the failure
mode is purely "the `cc` that ran had no SDK", not anything about the APE.)

**Remedy for the user's Mac** (either one):

1. Install the Command Line Tools so `cc` has a working SDK, then just run the
   APE again (first run compiles `$TMPDIR/.ape-1.10`, later runs reuse it):

   ```
   xcode-select --install          # or: xcode-select --switch /Applications/Xcode.app
   cc --version && xcrun --show-sdk-path   # both must succeed
   ./hello
   ```

2. Pre-build the loader once and install it as the systemwide `ape` command,
   which every APE prefers from then on (this is cosmo's own documented
   recommendation, `.cosmocc/3.9.2/README.md`: "Apple Arm64 users should
   compile `cc -O -o ape bin/ape-m1.c` and move `ape` to
   `/usr/local/bin/ape`"):

   ```
   cc -O -o ape pizfix/libexec/ape-m1.c && sudo mv ape /usr/local/bin/ape
   ```

Both remedies need the SDK once; there is no way to avoid that, since the
loader itself is a macOS program.

**What we verified about our pipeline vs upstream cosmo** (verdict: our APE
tooling is faithful; the assert.h failure is expected cosmo behavior on an
SDK-less Mac, not a Fil-C defect):

- Stub: our apelink's generated shell script is **byte-identical** to the one
  the upstream 3.9.2 `cosmocc` toolchain's apelink generates for the same
  inputs (hello built by real cosmocc, fed to both apelinks), modulo (a) the
  6-char anti-collision heredoc marker (`justineXXXXXX`), which apelink
  derives from a Blake2b digest over its inputs and which changed between
  cosmo 3.9.2 and the pristine snapshot vendored here (the 3.9.2 release
  hashed with crc32+BLAKE2B256 over a hashpool, the snapshot streams
  Hacl_Hash_Blake2b - also why the vendored `ape-x86_64.elf` differs from the
  3.9.2 tarball's; cosmo's own builds use the tree-built apelink/loader the
  same way we do), and (b) per-program values (our ELF entry/`e_phnum` in the
  stub's `printf`ed ELF headers, and dd offset digit widths for our larger
  Fil-C images).  The Darwin branch - the `cc` check, the
  `xcode-select --install` hint, the `dd | gzip -dc >"$t.c"`, and
  `cc -w -O -o "$t.$$" "$t.c"` - is identical.
- `ape-m1.c`: byte-identical across
  `projects/yolocosmo/ape/ape-m1.c` == `.cosmocc/3.9.2/bin/ape-m1.c` ==
  `pizfix/libexec/ape-m1.c` == the gzip'd source extracted back out of one of
  our fat APEs.  The aarch64 APE loader binary (`ape-aarch64.elf`) is also
  byte-identical to the 3.9.2 tarball's.
- The aarch64 payload is XNU-ready: `aarch64-ape` is built with
  `SUPPORT_VECTOR=255` (like `x86_64-ape`; on aarch64 dce.h folds that to
  Linux+XNU+FreeBSD - Windows/Metal are hard-zeroed there), so the XNU
  syscall machinery IS compiled into `pizfix/lib-aarch64/libyolocosmo.a`:
  the closure (`filc-objects-aarch64.mk`, generated by
  `compute-closure.py --mode aarch64-ape` against the full-SUPPORT_VECTOR
  cosmopolitan.a) includes `libc/intrin/ulock.o` (XNU ulock futexes),
  `libc/calls/sysctl.o`, `libc/sysv/calls/sys_sysctl.o`,
  `libc/runtime/getsysctl.o`, ...  Counterfactual check: in the
  `aarch64-optlinux` mode (`SUPPORT_VECTOR=1`, Linux-only) `ulock.o` is not
  built at all.  The pizlonated user libc stays `SUPPORT_VECTOR=1` (its raw
  asm/Win32 branches are what Fil-C cannot compile); that is fine for XNU
  because every syscall funnels through the yolo side (the `zsys_*` shims),
  and `__hostos` detection at boot is yolo-side (upstream-tested).  aarch64
  Linux behavior is unchanged by all this (XNU code is selected at runtime
  via `__hostos` and never executes on Linux): hello, pthreadcleanup,
  a 4-thread pthread+TLS test, and cpphashtablegctest{,2,3} all pass under
  `qemu-aarch64` after a fresh build.
- Still untested on real macOS hardware end-to-end (the SDK-less failure
  above is from a user Mac): after the loader compiles, cosmo's XNU boot for
  the aarch64 payload is upstream-cosmo machinery.  If something fails after
  the loader is running, `pizfix/libexec/ape-m1.c` compiled with `-g` plus
  the `.aarch64.elf` image are the debugging artifacts.

## Escape hatches and knobs

- `--filc-cosmo` - force cosmo mode even if the marker probe says otherwise.
  Requires a pizfix tree (add `--filc-resource-dir=<path>` to point at one).
  Useful for testing a cosmo pizfix tree at a nonstandard location without
  replacing your real one, e.g.
  `clang --filc-cosmo --filc-resource-dir=/tmp/pizfix-cosmo -o hello hello.c`.
  Without a pizfix tree it fails with ``'--filc-cosmo' requires a Fil-C
  pizfix directory (point at one with '--filc-resource-dir=')``.
- `--filc-no-ape` - the public off switch for all of the APE machinery: links
  produce only the static ELF (no fat APE, no side files) and compiles
  produce only the requested object (no `.aarch64/` shadows).  This is what
  the cosmo runtime builds themselves use (libpas, projects/usercosmo,
  build_cxx.sh), since they build each architecture explicitly.  (It is also
  what the driver's nested aarch64 pipeline passes internally.)
- `--filc-ape` - a single-architecture APE at `<output>` with the ELF at
  `<output>.dbg` (and no shadow compiles).
- `COSMOARCHES` - the list of cosmo architectures built by
  `build_yolocosmo.sh` and `build_usercosmo.sh`
  (`COSMOARCHES="x86_64 aarch64"` by default).  The per-arch cosmo mode is
  always `<arch>-ape`; there is no separate mode knob.
- `FORCE=1 ./build_usercosmo.sh` - rebuild the pizlonated cosmo libc from
  scratch (header dependency tracking is not done, so use this after editing
  widely-included headers).
- `filc/run-tests` accepts `--filter <regex>`, `--test <name>`, `--verbose`,
  `--no-run`, and `--pizfix <dir>`, like in the other flavors.

## Limitations and notes

- Cosmo mode is static-only: no `-shared`, no `-pie`, no dlopen (see above).
- The APE payload itself is OS-agnostic by construction, but this repo only
  exercises Linux (x86_64 host, plus aarch64 via qemu or real hardware).
  Windows execution was verified under wine (see the WINDOWS STATUS bullet
  below); macOS execution of the produced APEs has not been run on real
  hardware here, but the macOS loader story is verified against upstream and
  documented above ("Running on macOS (Apple Silicon)" - the loader-source
  compile needs the macOS SDK, which is expected cosmo behavior).
- TLS in the payload is portable: the yolo libc is built with cosmo's tlscc
  (so every `%fs:0` TLS access goes through the per-OS `__get_tls_rXX`
  dispatch helpers), libpas' fast TLS uses a pthread key under PAS_COSMO, and
  the pizlonated libc's TIB is per-filc-thread zgc memory found through the
  zthread cookie instead of a `__thread` variable.  A static x86_64 cosmo
  binary therefore contains no TLS codegen that touches `%fs` directly; the
  only remaining `%fs` instructions live in per-OS-guarded assembly
  (`libc/sysv/tlsasm.S` helpers, `vfork.S`'s non-Windows path, and
  `systemfive.S`'s Linux paths), which is exactly how cosmo's own default
  x86_64 build stays Windows-safe.  Known punted exceptions: `__thread` /
  `thread_local` variables in pizlonated code still lower to `%fs` TLS
  accesses (the Fil-Pizlonator's thread-local cache pointer), so cosmo
  programs that actually use C/C++ `thread_local` - and the handful of
  usercosmo/libc++abi internals that do (trace.c, memoryexists.c, unveil.c,
  fexecve.c, h_errno.c, `__cxa_get_globals`) - will still fault on Windows;
  they work on Linux.  libyolort (compiler-rt builtins, which is shared with
  the other flavors) also carries `%fs:0x28` stack-canary code from the host
  toolchain.
- `apelink`/`pecheck` are x86_64 Linux host tools (they are built in cosmo's
  Linux-only `x86_64-optlinux` mode), as are minilute and sarcasm.
- aarch64 APEs (single-arch) embed the Apple-silicon loader source
  (`ape-m1.c`) so they can run on arm64 macOS; they carry no PE header, so
  `pecheck` is not meaningful for them.  Fat APEs carry the x86_64 PE header
  and pass `pecheck`.
- First cosmo build downloads ~1.2GB of toolchain into
  `projects/yolocosmo/.cosmocc` (needs network + `unzip`).
- The aarch64 cosmo link wants `aarch64-linux-gnu-ld` (from
  `binutils-aarch64-linux-gnu`/`gcc-aarch64-linux-gnu`); the driver falls back
  to `ld.lld` when it is missing.
- After changing what the payload references from the yolo libc (new symbols
  in libpizlo.a/libc.a/libc++*.a, or cosmo config changes that affect TLS),
  re-verify the closure and rebuild the slim archive:
  `python3 projects/yolocosmo/filc/compute-closure.py --mode x86_64-ape`
  (and `--mode aarch64-ape` for cross builds), then rerun
  `build_yolocosmo.sh`.  Remember that changing TLS-bearing yolo flags (like
  `TLSCC`) does not rebuild anything by itself - force it with
  `make m=x86_64-ape filcyolo -B`.
- WINDOWS STATUS (round 2, verified under WINE - see /tmp/usercosmo_notes.md
  for the full recipe): a local wine64 harness (`apt-get install wine64`,
  `WINEPREFIX=/tmp/wineprefix WINEARCH=win64 wineboot --init`, then
  `WINEDEBUG=-all wine ./prog` on the fat APE) runs the whole stack: APE
  loader, cosmo crt, libpizlo, stdio, threads, C++.  Fixed on the way, all
  cosmo/Wine-specific and gated so musl/glibc are untouched:
  + filc_start_program's RLIMIT_STACK assert: cosmo's getrlimit() on Windows
    reads the PIB's inverted rlimit table = RLIM_INFINITY = -1 as intptr_t;
    infinite/below-min is now replaced with 8 MiB (#if PAS_COSMO).
  + cosmo mmap() on Wine: __maps_pickaddr() deterministically picked an
    address inside Wine's DLL region and the EFAULT retry loop spun forever;
    after one re-pick it now falls back to letting the OS choose (tracked
    normally afterwards).  Real Windows never hit this (nothing lives at the
    pick), but Wine does because cosmo cannot see foreign mappings.
  + recursive-mutex reentry (hit on Linux too): cosmo's stdio FILE locks are
    RECURSIVE and their reentry check compares MUTEX_OWNER(word) against
    tib_ptid of the cookie TIB; the phony main thread's tib_ptid was 0,
    matching an unlocked recursive mutex's zero owner, so the main thread
    skipped the nsync lock entirely once any other thread printed
    concurrently (duplicated output, negative fwrite memmoves, nsync panics).
    filc_setup_main_thread() now sets tib_ptid = zthread_self_id() (and
    deliberately NOT tib_ctid: _pthread_decimate() treats zero tib_ctid as
    "stack free" and the decimate walk relies on stopping at the main pt).
  + yolo_futex_wait/wake used the raw sys_futex thunk (ENOSYS off-Linux ->
    spinning waits, dead wakes); they now use cosmo_futex_wait/wake.
  + filc_unmap's mmap(MAP_FIXED)-over trick cannot work on cosmo-Windows
    (VirtualAlloc refuses already-committed pages; GC decommits split the
    tracked maps), so on Windows it zeroes the memory instead - same
    contract; cosmo's Windows madvise(MADV_DONTNEED) also zeroes now, since
    libpas' decommit zero-mode assumes DONTNEED pages read back zero.
  Wine results: helloraw "Hello!" exit 0; loop still looping at timeout;
  4-thread pthread test counter=4000 exit 0; C++ iostream/thread/exceptions
  exit 0.  Residual known flake: a 4-thread printf stress still fails ~1/40
  natively with the same double-entry signature (suspected Linux tid reuse
  vs stale MUTEX_OWNER in a recursive mutex; not a gate failure).
- Windows retest checklist for the next person with a Windows box (things
  wine cannot fully emulate): rerun the same fat APEs on real Windows and
  expect the same behavior as under wine; GC-heavy programs and signals/
  fork remain unproven there (see /tmp/usercosmo_notes.md "Expected next
  layers").  If the boot still fails, WinDbg's faulting address maps 1:1
  onto the `.com.dbg` image (same load base), so symbolize with
  `nm -n helloraw.com.dbg`.

## Verification checklist

Run through this after a fresh cosmo build to confirm everything works:

1. Flavor state: `ls pizfix/lib/libyolocosmo.a pizfix/lib-aarch64/libyolocosmo.a`
   both exist (and `pizfix/lib/libc.so.6666` does not - that's the glibc
   marker).  `pizfix/libexec/` contains `apelink`, `pecheck`, `ape-m1.c`.
2. Test suite: `filc/run-tests` - the runner probes the flavor and skips
   what cosmo cannot do (`Skipping <name>, ...` lines): currently 83 tests
   marked `unsupportedOnCOSMO`, 39 tests that build shared libraries, and a
   couple of plain skips.  Everything else runs and passes; the final line is
   `SUCCESS` (each test prints a dot in the default mode).  On this tree that
   was 6445 tests executed, all green (the count grows as tests are added;
   the full gate takes ~10 minutes on a warm 32-core box).
3. Default fat APE: `clang -o hello hello.c && ./hello` (the fat APE runs);
   `head -c 6 hello` shows `MZqFpD`; `pizfix/libexec/pecheck hello` exits 0;
   `file hello.com.dbg` says a statically linked x86-64 ELF; and
   `qemu-aarch64 ./hello.aarch64.elf` runs the aarch64 half.
4. aarch64: `clang --target=aarch64-linux-gnu -o helloarm hello.c &&
   qemu-aarch64 ./helloarm.dbg`.
5. Knobs: `clang --filc-fat-ape -o hello hello.c` behaves exactly like the
   default; `clang --filc-no-ape -o hello hello.c` gives a plain x86_64 ELF
   (`file hello` says ELF, with no side files and no shadow objects); and
   `clang --filc-ape -o hello hello.c` gives a single-architecture APE plus
   `hello.dbg`.
6. C++: `clang++ -o prog prog.cpp && ./prog` with an iostream/thread program.
7. Fat-APE macOS story (documented, no Linux action needed): the stub's
   Darwin branch compiles `ape-m1.c` with `cc -w -O` on first run and
   `pizfix/libexec/ape-m1.c` is byte-identical to
   `projects/yolocosmo/ape/ape-m1.c` and to the 3.9.2 toolchain's copy;
   `pizfix/lib-aarch64/libyolocosmo.a` contains the XNU objects
   (`nm pizfix/lib-aarch64/libyolocosmo.a | grep ulock` shows
   `T ulock_wait`/`T ulock_wake`).
